# LLM + DOCX 시험성적서 작성 가이드

## 0. 문서 개요

본 문서는 KAIC 시험원이 LLM(Claude 등)을 활용하여 시험성적서 docx 파일을 효율적으로 작성하는 워크플로우를 정리한 가이드이다. 본 가이드의 목표는 다음과 같다.

- 시험성적서 작성 시간을 단축하고 일관된 품질을 확보한다.
- LLM이 docx 양식을 직접 편집하도록 지시하는 표준 절차를 제공한다.
- 신규 시험원이 빠르게 작성 표준을 익히고 결과의 유효성을 보장할 수 있는 최소 퀄리티를 산출하도록 한다.
- 자주 발생하는 실수와 그 대응 방법을 정리한다.

본 가이드는 KAIC 표준양식(KAIC-F-7.8-08 등)을 기준으로 작성되었으며, 다른 양식을 사용할 경우 항목 매핑은 시험원이 조정한다.

---

## 1. 작업 환경 준비

### 1.1 표준양식 docx 확보(표준 SW 문서는 방선임 제공)

KAIC가 관리하는 시험성적서 표준양식 docx 파일을 작업 시작 전에 확보한다. 본 양식은 시험 종류에 따라 다르므로 본인 시험에 해당하는 양식을 사용한다.

### 1.2 시험 설계 문서 사전 작성

시험성적서는 시험 설계 문서를 바탕으로 결과를 정리하는 산출물이다. 시험성적서 작성에 들어가기 전에 다음 문서가 완성되어 있어야 한다.

| 문서 | 역할 |
|---|---|
| GT (Ground Truth) | 각 시험 항목의 GT 판정 기준 |
| 시험절차서 | 시험자가 수행할 단계와 채취할 증적의 정의 |
| 채점표 | 시험 수행 결과를 단계별로 기록 |

위 3종이 GT 문서를 단독 참조하면서 일관되게 작성되어 있지 않으면 시험성적서 작성 단계에서 측정 함수 정의가 흔들리거나 결과표의 분모/분자가 어긋난다.

### 1.3 LLM 도구 선택

docx 파일을 직접 편집할 수 있는 LLM 도구를 사용한다. 본 가이드는 Claude를 기준으로 작성되었으나, docx 파일을 unpack → XML 편집 → repack 할 수 있는 도구라면 어느 것이든 적용 가능하다.

## 2. 시험의 종류 확인 [작성 시작 전 필수]

시험성적서는 시험 종류에 따라 적용 규격, 갑지 하단 안내문, KOLAS 마크 사용 여부, 인정 범위 외 표시(`*`) 등이 모두 달라진다. 작성을 시작하기 전에 본 시험이 어느 종류에 해당하는지 반드시 식별한다.

### 2.1 KAIC 시험 종류

현재 KAIC가 수행하는 주요 시험 종류는 다음과 같다.

- KS X ISO/IEC 25023:2016 기반 소프트웨어 품질 측정 시험
- KS X ISO/IEC 25024:2015 기반 데이터 품질 시험 (인정 확대 추진 중)
- ISO/IEC TS 4213 기반 AI 분류 성능 시험 (인정 확대 추진 중)
- 그 외 자체 규격 시험

### 2.2 시험 종류에 따른 처리

시험 종류에 따라 다음 항목이 결정된다. 세부 적용 기준은 KAIC 내부 기준 문서를 참조한다.

- 적용 규격 표기
- 갑지 최하단 안내문 문구
- KOLAS 마크 사용 여부
- 인정 범위 외 시험의 결과란 `*` 표시 필요 여부

위 사항을 모르는 경우 시험성적서 작성에 들어가서는 안 된다. 시험 종류와 그에 따른 작성 기준은 시험원이 사전에 숙지하고 있어야 할 기본 사항이다.

## 3. 시험성적서 작성 워크플로우

### 3.1 시험 설계 문서로부터 데이터 추출

GT, 시험절차서, 채점표에서 시험성적서에 들어갈 데이터를 추출한다. 주요 추출 대상은 다음과 같다.

| 데이터 | 출처 |
|---|---|
| 측정 항목 ID 및 이름 (예: FCr-1-G 기능 정확성) | GT |
| 측정 함수 X = A/B 정의 | GT |
| B 값 및 산정 근거 | GT |
| 시험 대상 기능 명세 (시스템 기능 인벤토리) | GT 또는 시스템 분석 결과 |
| 시험 수행 절차 | 시험절차서 |
| 단계별 GT 기준 | GT |
| 시험 결과 (A 값, 측정값 X) | 채점표 |

추출한 데이터를 한 문서에 정리해두면 LLM에게 작업을 지시할 때 일관된 입력으로 사용할 수 있다.

### 3.2 LLM에게 docx 편집 지시

LLM에게 docx 파일을 첨부하면서 어떤 항목을 어떻게 수정할지 지시한다. 지시는 다음 원칙을 따른다 (자세한 사항은 §4 참조).

- 한 번에 한 항목씩 지시한다.
- 각 단계 후 LLM이 docx 검증(pack.py 등)을 수행하도록 한다.
- 표 구조는 가급적 손대지 않고 텍스트만 교체하도록 지시한다.

### 3.3 패킹·검증

LLM이 모든 수정을 완료하면 docx 파일을 최종 패킹·검증한다. 검증 통과 후 본인이 직접 docx를 열어 시각적으로 확인한다.

## 4. LLM 지시 시 원칙

### 4.1 짧은 단위로 끊어서 작업

한 번에 너무 많은 변경을 지시하면 LLM이 의도와 다른 부분을 건드릴 수 있다. 다음과 같이 작업 단위를 작게 끊는다.

- "시험결과 요약 영역의 분모 4를 10으로 바꿔라"
- "시험방법 부제의 측정 항목 부제목 텍스트를 다음으로 교체해라"
- "시험대상 기능 확인표의 10개 행 데이터를 다음으로 교체해라"

각 단계 후 결과를 확인하고 다음 단계로 진행한다.

### 4.2 매 단계 검증

각 변경 후 docx 무결성을 검증한다. Claude의 docx 스킬은 `pack.py`로 자동 검증을 수행하며, "All validations PASSED" 메시지가 나오는지 확인한다.

검증에 실패하면 즉시 어떤 변경에서 깨졌는지 파악하고 수정한다. 한 번 무결성이 깨진 채로 추가 변경을 누적하면 디버깅이 어려워진다.

### 4.3 표 구조 손대지 말고 텍스트만 교체 우선

기존 표의 행 수가 동일하거나 더 적게 줄어드는 경우, 표 구조 자체는 손대지 말고 셀 내부 텍스트만 교체하도록 지시한다. 행 수를 늘려야 하는 경우에만 표 행 추가 작업을 수행한다.

표 셀이 여러 `<w:r>` 런으로 분할된 경우 단순 문자열 치환이 실패할 수 있다. 이때는 LLM이 셀 단위로 XML을 다시 작성하도록 지시한다.

### 4.4 XML 엔티티 주의

docx 내부는 XML이다. 본문 텍스트에 다음 문자가 들어가면 반드시 XML 엔티티로 치환되어야 한다.

| 문자 | XML 엔티티 |
|---|---|
| `<` | `&lt;` |
| `>` | `&gt;` |
| `&` | `&amp;` |
| `"` | `&quot;` |
| `'` | `&apos;` |

특히 `<JWT>`, `<타 계정 ID>` 같이 꺾쇠를 포함한 표현은 그대로 넣으면 docx 검증이 실패한다. LLM에게 이러한 표현을 넣을 때는 반드시 엔티티 처리하도록 지시한다.

## 5. 실제결과 및 시험결론 작성 방식 선택

### 5.1 표 vs 본문 서술 판단 기준

측정 항목의 세부 항목 수에 따라 표 또는 본문 서술 중 하나를 선택한다.

| 세부 항목 수 | 권장 방식 | 이유 |
|---|---|---|
| 3개 미만 (1~2개) | 본문 서술 | 표를 만들 가치가 없음. 한 단락으로 충분 |
| 3개 이상 | 표 | 시각적으로 정리하기 좋음 |

3개도 경계선이므로 시험원 판단에 따라 본문 서술로 가도 무방하다. 다만 항목 수가 5개 이상이면 표가 강하게 권장된다.

### 5.2 표 형식 작성 시 권장 컬럼

표를 사용하는 경우 다음 컬럼 구조를 권장한다.

| No | 측정 항목 | 세부 시험 결과 | 적합 여부 |
|---|---|---|---|
| 1 | (측정 항목 이름) | (N/N 형식, 예: 4/4) | (적합/부적합) |

- **세부 시험 결과**: 해당 측정 항목 내의 세부 시험 단계 수를 `N/N` 형식으로 표기 (예: 4/4, 11/11). 모든 세부 단계가 GT와 일치했음을 의미.
- **적합 여부**: 측정 항목 단위의 최종 판정. 모든 세부 단계가 일치하면 "적합", 한 단계라도 어긋나면 "부적합".

### 5.3 본문 서술 작성 시 권장 구조

본문 서술을 선택하는 경우 다음 요소를 한 단락에 포함한다.

- 적용 규격 (KS X ISO/IEC 25023:2016 등)
- 측정 함수 정의 (X = A/B)
- 시험 대상의 개수 및 식별 근거
- 결과 요약 (A/B 값, 측정값 X)

예시:
> 본 시험은 KS X ISO/IEC 25023:2016 8.5.3 운영성 측정에 따라 (시스템명)의 어드민 운영 시나리오에서 모니터링 능력이 이점이 될 기능 3개(접수 통계 / 실시간 신규 접수 감지 / 처리 이력 추적)를 식별하여 각 기능의 모니터링 구현 여부를 GT 문서와 비교 검증하였음. 시험 결과 3개 모니터링 영역의 구현 여부를 확인함.

### 5.4 잘못된 결과표 작성 사례 (금지 패턴)

다음과 같은 패턴은 양식 검토에서 지적될 수 있는 잘못된 작성 사례이다.

#### 5.4.1 시험대상 기능 확인표 구조를 결과표에 그대로 베끼는 경우

시험대상 기능 확인표(시험방법 섹션)와 결과표(시험결과 섹션)는 목적이 다르다.

- **시험대상 기능 확인표**: 시험 시작 전, 시스템에 어떤 기능이 있는지를 명세하는 기능 인벤토리. 컬럼은 `대분류 / 중분류 / 소분류 / 세세분류(또는 하위분류) / 기능설명`.
- **결과표**: 시험 수행 후, 측정 함수 X = A/B의 산정 근거를 보여주는 측정 결과. 컬럼은 `No / 측정 항목 / 세부 시험 결과 / 적합 여부` 형식이 권장됨.

두 표는 컬럼 구조가 달라야 한다. 시험대상 기능 확인표의 6컬럼 구조를 결과표에 그대로 가져다 쓰고 마지막에 "확인 내용" 칸 하나만 추가하는 식의 작성은 측정 함수 산정 근거를 명확히 보여주지 못하므로 지양한다.

#### 5.4.2 측정 함수 정의와 어긋나는 결과표

결과표의 행 수와 측정 함수의 B 값이 일치해야 한다. 예를 들어 FCr-1-G의 B=10이면 결과표는 10행이어야 한다. 행 수가 다르면 측정 함수와 결과표가 어긋나 검토자가 A/B 산정 근거를 파악할 수 없다.

## 6. 측정 함수 X = A/B 작성 원칙

### 6.1 B 값 산정 근거 명시

GT 문서에서 측정 항목의 B 값이 왜 그 숫자인지 산정 근거가 명시되어 있어야 한다. 시험성적서에는 B 값과 그 산정 근거가 시험방법 또는 시험기준 섹션에 일관되게 반영되어야 한다.

표준의 비고에 든 예시(예: "데이터 위조 방지 기법에는 백업·참고 비교·미러링이 있다")를 그대로 B 값으로 사용하지 않는다. 본 시스템에서 사용 가능하고 권고되는 기법을 시스템 분석 결과로 식별한 결과가 B 값이 되어야 한다.

### 6.2 A 값은 시험 후 확정

A 값(부정확 기능 수 또는 구현된 기법 수)은 시험 수행 후 채점표 결과에서 산출된다. 시험성적서 작성 시점에 A 값이 확정되지 않았으면 빈칸으로 두고 시험 종료 후 채워 넣는다.

### 6.3 세부시험 단위 vs 결과표 단위 구분

판정은 두 단계로 나뉜다.

| 단계 | 단위 | 판정 라벨 |
|---|---|---|
| 세부시험 | 채점표의 각 단계 (예: #4-1, #4-2, #4-3) | 정확/부정확 또는 적합/부적합 |
| 결과표 | 측정 항목 단위 (예: #4 전체) | 적합 여부 |

세부시험 단계는 GT 일치 여부에 따라 정확/부정확으로 판정하고, 결과표는 그 세부시험들이 모두 정확하면 "적합", 하나라도 부정확하면 "부적합"으로 판정한다.

### 6.4 세부시험 수량 명시

각 측정 항목의 "세부 시험 내용 및 증적" 섹션 앞에 본 시험의 세부시험 수량을 명시한다.

예: "본 시험의 세부시험은 10종입니다."

이는 검토자가 측정 함수 B 값과 세부시험 수량의 일치 여부를 한눈에 확인할 수 있게 한다.

## 7. 자주 발생하는 문제와 대응

### 7.1 XML 엔티티 깨짐

**증상**: pack.py 검증에서 "Specification mandates value for attribute" 같은 오류 발생.

**원인**: 본문 텍스트에 `<` 또는 `>`가 포함되어 XML 파서가 태그로 해석함.

**대응**: 해당 부분을 `&lt;` / `&gt;`로 치환. 본인이 LLM에게 새 텍스트를 줄 때부터 엔티티로 작성해주는 것이 안전.

### 7.2 셀이 여러 run으로 분할되어 있을 때

**증상**: LLM이 셀 텍스트 단순 치환을 시도했는데 변경이 안 됨.

**원인**: 한컴 또는 LibreOffice 변환 과정에서 한 셀 내부의 텍스트가 여러 `<w:r>` 런으로 쪼개져 저장됨. 단순 문자열 검색으로 원본을 찾을 수 없음.

**대응**: 셀 단위로 모든 런을 합쳐서 새 텍스트로 치환하도록 LLM에게 지시. 또는 unpack 스크립트가 자동으로 인접 런을 병합해주는 옵션을 사용한다.

### 7.3 LLM이 측정 함수 정의를 왜곡할 때

**증상**: LLM이 결과표를 임의로 재해석하여 측정 함수와 어긋난 형태로 만듦.

**원인**: LLM이 docx 안의 기존 잘못된 표 구조를 그대로 따라하거나, 본인 추론으로 표준을 재해석함.

**대응**: GT 문서를 LLM에게 함께 제공하고 "이 GT 문서의 측정 함수 정의를 단독 참조하라"고 명시. 결과표 형태도 본 가이드 §5.2의 권장 컬럼을 명시적으로 지시한다.

### 7.4 docx 변환·편집 후 양식 일부가 깨지는 경우

**증상**: docx를 열었을 때 헤더 영역(KAIC 로고/주소/성적서 번호)이 페이지 테두리 밖에 표시되거나, 페이지 번호 위치가 어긋남.

**원인**: MS Word의 페이지 테두리 기본값이 본문 영역에만 적용되도록 설정되어 있어 헤더/푸터 영역까지 테두리가 그려지지 않음.

**대응**: 본 가이드 §10.1 페이지 테두리 머리글 포함 처리 참조. 이 작업은 최종 PDF 변환 전에 반드시 수행한다.

## 8. 본인이 직접 해야 할 일 (자동화 불가 영역)

LLM이 처리할 수 없거나 처리해서는 안 되는 다음 항목은 시험원이 직접 처리한다.

### 8.1 증적 이미지 삽입

시험 수행 중 채취한 화면 캡처를 docx에 삽입하는 작업. MS Word에서 "삽입 → 그림"으로 직접 처리한다. LLM이 처리할 수도 있지만 시험원이 어느 캡처를 어느 자리에 넣을지 결정하는 것이 더 빠르다.

### 8.2 SHA-512 해시값 입력

시험기록별지의 "시험대상품목 HASH (SHA-512)" 항목. 제출 zip 파일의 해시를 계산하여 직접 입력한다.

### 8.3 시험 일시·시험자명·서명

시험 일시, 시험 장소, 시험자명, 선임 실무자, 기술책임자 서명 등 시험 수행 결과로 확정되는 항목은 시험 종료 후 본인이 직접 채워 넣는다.

### 8.4 시험기록별지의 데이터 레코드 관리

Windows Process Monitor 추출 데이터 등의 별지 부속 자료는 시험원이 직접 채취·붙여넣기 한다.

## 9. 검증 체크리스트

시험성적서 작성 완료 후 제출 전 다음 항목을 점검한다.

- [ ] docx 무결성 (pack.py가 "All validations PASSED" 출력)
- [ ] 측정 함수 X = A/B 정의가 시험기준·시험방법·결과표에서 일관됨
- [ ] B 값 산정 근거가 명시됨
- [ ] 결과표의 행 수와 B 값이 일치함
- [ ] GT 문서와 결과표의 단계 매핑이 일치함
- [ ] 시험대상 기능 확인표가 시스템 기능 명세와 일치함
- [ ] 시험대상 기능 확인표와 결과표가 다른 컬럼 구조를 가짐
- [ ] 각 측정 항목별 세부시험 수량이 명시됨
- [ ] 시험 일시·시험자·서명 영역 누락 없음
- [ ] 증적 이미지가 올바른 위치에 삽입됨
- [ ] SHA-512 해시값 입력됨

## 10. 최종본 PDF 제출 전 처리 사항

### 10.1 페이지 테두리 머리글 포함 처리 [필수]

**증상**: 시험성적서 docx를 Word에서 열면 헤더(KAIC 로고/주소/성적서 번호)가 페이지 테두리 밖에 표시됨.

**원인**: MS Word의 docx 페이지 테두리 기본 적용 동작. 표준 설정에서는 본문 영역에만 테두리가 그려지고 헤더/푸터 영역은 테두리 밖으로 빠진다.

**조치**: Word에서 다음 경로로 설정 변경.

> 디자인 → 페이지 테두리 → 옵션 → "머리글 포함" 체크 → 확인

이 옵션을 켜야 헤더 영역까지 테두리가 그려진다. 미조치 시 PDF 변환 후 모든 페이지의 헤더가 테두리 밖에 표시되어 양식 검토에서 불합격된다.

### 10.2 시험 종류별 최종 점검 [필수]

본 시험의 종류에 따라 다음 항목을 확인한다.

- KOLAS 마크 적용 여부가 시험 종류에 맞는가
- 갑지 최하단 안내문이 본 시험 종류에 맞는 문구인가
- 인정 범위 외 시험의 경우 결과란에 `*` 표시가 들어가 있는가

세부 적용 기준은 KAIC 내부 기준 문서에 따르며, 시험원이 사전에 숙지하고 있어야 한다.

### 10.3 PDF 변환

Word에서 다음 경로로 PDF로 변환한다.

> 파일 → 내보내기 → PDF/XPS 문서 만들기

또는 인쇄 → 프린터를 "Microsoft Print to PDF"로 선택 → 인쇄.

### 10.4 최종 PDF 시각 검토

생성된 PDF를 열어 다음 사항을 확인한다.

- 모든 페이지의 헤더 영역(KAIC 로고/주소/성적서 번호)이 페이지 테두리 안에 있음
- 페이지 번호 `[n/m]`이 정상 표시됨
- 표가 페이지 경계에서 깨지지 않음
- 폰트가 의도한 대로 렌더링됨 (특히 본문 한글 폰트)
- 증적 이미지가 잘리거나 흐려지지 않음

위 검증을 통과하면 시험성적서 작성이 완료된다.
